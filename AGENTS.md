# AGENTS.md

Guidelines for everyone (humans and AI agents) changing this repository. They
describe the standard changes are held to. [DEVELOPMENT.md](DEVELOPMENT.md)
covers the development setup and how to run the checks, and is not repeated
here.

## Standards and sources

Changes follow these sources. If they contradict each other, the higher
entry wins:

1. The Home Assistant developer documentation, in particular the
   [Integration Quality Scale](https://developers.home-assistant.io/docs/core/integration-quality-scale/)
   with its [rules](https://developers.home-assistant.io/docs/core/integration-quality-scale/rules)
   and [checklist](https://developers.home-assistant.io/docs/core/integration-quality-scale/checklist).
   The sources are in
   [home-assistant/developers.home-assistant](https://github.com/home-assistant/developers.home-assistant/tree/master/docs/core/integration-quality-scale).
2. This file, the repository configuration (`ruff.toml`, `mypy.ini`,
   `pytest.ini`, the CI workflows) and [DEVELOPMENT.md](DEVELOPMENT.md).
3. The skill
   [ha-integration-dev](https://github.com/tonylofgren/aurora-smart-home/tree/main/ha-integration-dev)
   from aurora-smart-home, used as a practical reference for patterns,
   checklists and tests. It was reviewed at commit `bdf9802` (2026-11-05).

Notes on using the skill in this repository:

- Its quality scale summary (`references/publishing.md`) doesn't match the
  official rules: it lists diagnostics, reconfiguration and repair issues
  under Silver, while they belong to Gold. Always use the official rules.
- Its attribution banners ("Generated by …") are not added to files in this
  repository.
- It treats `DataUpdateCoordinator` as the default. This integration is push
  based over a persistent Bluetooth connection, and `CasambiApi` takes the
  coordinator's role. Don't add a polling coordinator.
- It requires `aiohttp` for HTTP. `casambi-bt` uses `httpx`, so pass the client
  from Home Assistant's `get_async_client(hass)` and never create your own
  (rule `inject-websession`).

## Quality scale

This is a custom integration, so it belongs to the special tier "Custom" and
can't be graded officially. We still hold it to the scaled tiers:

- [`quality_scale.yaml`](custom_components/casambi_bt/quality_scale.yaml) is
  the source of truth for the status of every rule.
- No change may turn a `done` rule into a gap. New code must satisfy every
  rule that is `done`.
- Mark a rule `done` only if the code and a test show it. Mark it `exempt`
  only with a comment that names the official exception. Mark it `todo` with
  a comment that says what is missing.
- Update `quality_scale.yaml` in the same pull request that changes the status
  of a rule.
- Refer to rules by their ID (e.g. `log-when-unavailable`) in commits and pull
  requests.

## Project overview

- `custom_components/casambi_bt/` is a Home Assistant custom integration
  (HACS) for Casambi lighting networks over Bluetooth LE.
- All Bluetooth, Casambi protocol and cloud handling lives in the library
  `casambi-bt` (`CasambiBt`). The integration pins an exact version in
  `manifest.json` and the same version in `requirements_test.txt`.
- `CasambiApi` (`__init__.py`) owns the connection, the reconnect logic, the
  network refresh and all library callbacks. It is stored in the typed
  `entry.runtime_data` (`CasambiConfigEntry`).
- Entities (`entity.py` and the platform modules) only read state from
  `CasambiApi` and send commands through it. They never use the library
  directly.
- `config_flow.py` holds the user, Bluetooth discovery, reauth, reconfigure
  and options flows. `migration.py` migrates config entries and the cache.
  `diagnostics.py` and `services.py` provide diagnostics and the actions.

## Branches and pull requests

- `main` is the release branch. Only `dev` is merged into `main`, which CI
  enforces (`branch_check.yaml`).
- Target `dev` with all changes. Work on a topic branch.
- One concern per pull request. Bug fixes, features and refactorings go into
  separate pull requests.
- Fix a problem where it originates. If the cause is in `casambi-bt`, fix it
  there (see [Library changes](#library-changes)). Add a workaround in the
  integration only if users need it before a library release, and comment it
  as such.

## Compatibility

Users update in place. A change must not break an existing installation:

- Never change the format of a unique ID (config entries, devices or
  entities). The entity IDs and the history of users depend on it.
- Never rename or remove an action, an action field, a translation key used
  in automations or an option.
- A change of the stored config entry data needs a new config entry version
  and a migration in `async_migrate_entry`, with a test. New options need a
  default that keeps the previous behavior.
- Keep caches written by older versions readable, or migrate them
  (`migration.py`).
- If a change is visible to users (e.g. a different device class), say so in
  the pull request and in the release notes.

## Quality gates

Every change must pass the same checks as CI before it is pushed:

```bash
ruff check .
ruff format --check .
mypy custom_components/casambi_bt
pytest tests/ --cov=custom_components/casambi_bt --cov-report=term-missing --cov-fail-under=95
```

- CI also runs `hassfest` and the HACS validation.
- The test dependencies are listed in `requirements_test.txt`. CI runs them
  with Python 3.14.
- Don't relax the configuration (`ruff.toml`, `mypy.ini`, `pytest.ini`, the
  coverage threshold) to get a change through. Prefer a targeted
  `# noqa: <rule>` or `# type: ignore[<code>]` with a reason.

## Code style

- Follow the existing structure, naming and typing. Ruff's rule set mirrors
  Home Assistant core (`ruff.toml`, Google-style docstrings). `ruff format`
  decides the formatting.
- The code targets Python 3.14, like Home Assistant. Use its syntax (e.g.
  `except A, B:`) and don't add compatibility code for older versions.
- `mypy` runs in strict mode. Type everything. `cast()` is fine where the
  library is loosely typed, but don't silence real type errors.
- Code comments, docstrings, log messages and commit messages are in English.
- Keep changes minimal and focused. No drive-by refactorings, renames or
  formatting changes in unrelated code.

## Home Assistant practices

- **No blocking calls in the event loop.** File system access (e.g. the
  cache under `.storage/casambi_bt`) goes through
  `hass.async_add_executor_job`. Network and Bluetooth calls are always
  awaited.
- **Config entry lifecycle.** Raise the matching exception during setup:
  - `ConfigEntryNotReady` for transient Bluetooth or cloud problems,
  - `ConfigEntryAuthFailed` for rejected credentials (starts reauth),
  - `ConfigEntryError` only for permanent errors.

  Everything set up in `async_setup_entry` must be undone in
  `async_unload_entry`. Data stored outside the config entry is cleaned up in
  `async_remove_entry`.
- **Background tasks** are created with
  `entry.async_create_background_task`, so they are cancelled on unload. Home
  Assistant starts them eagerly by default: the coroutine runs synchronously
  up to its first `await`, even inside a library callback. Pass
  `eager_start=False` when the task must not run before the caller returns.
- **Availability.** Entities are push-based (`should_poll = False`). Every
  change of the connection state must reach the entities through a callback,
  otherwise they show stale state. A disconnect makes all dependent entities
  unavailable, a reconnect makes them available again. Log both once at
  `info` (rule `log-when-unavailable`).
- **Entity descriptions** are dataclasses with `frozen=True, kw_only=True`.
- **Time and attributes.** Use `homeassistant.util.dt` (`dt_util.utcnow()`)
  instead of `datetime.now()`. State attributes only hold JSON-serializable
  values.
- **Errors shown to users.** Entity commands and actions raise
  `HomeAssistantError` (or a subclass) with a `translation_key` when they fail
  (rules `action-exceptions` and `exception-translations`).
- **Translations.** Every user-facing string goes into `strings.json` and
  `translations/en.json`, every icon into `icons.json`. Also update the other
  translations (`de.json`, `nl.json`) if you can translate reliably. Otherwise
  leave them unchanged. `tests/test_translations.py` checks that the keys
  match.
- **Logging.**
  - `debug` for details,
  - `info` for rare state changes (connect, reconnect, reload),
  - `warning` for problems that recover on their own,
  - `error` or `exception` only for problems that need user action. Prefer a
    repair issue for those.

  Never log passwords, session tokens or keys. Casambi network data may
  contain the owner's email address, so log it at `debug` level only and
  redact it in diagnostics.

## Bluetooth rules

- Get devices from Home Assistant: use
  `bluetooth.async_ble_device_from_address(hass, address, connectable=True)`.
  Never scan or create `BleakScanner` instances yourself. Connections go
  through `bleak-retry-connector` in the library.
- Expect every backend: local BlueZ adapters and ESPHome Bluetooth proxies
  behave differently. In particular:
  - Proxies raise a bare `TimeoutError` and word errors differently (e.g.
    `"<device> is not connected"`). Never match error messages, check the
    connection state instead.
  - Proxies have a limited number of connection slots. Always disconnect
    connections that are no longer needed, also after failed attempts.
  - BlueZ keeps stale state (e.g. notify sessions) if a client is not
    disconnected after the link was lost.
- The disconnect callback is the only reliable signal for a lost link. There
  is no keep-alive, so code must not assume that `connected` is up to date
  while that callback is running.
- habluetooth drops advertisements that didn't change. An advertisement
  callback is therefore no reliable reconnect trigger. A reconnect started
  after a disconnect must keep retrying with backoff until it succeeds or the
  entry is unloaded. It must never stop silently, also not on unexpected
  errors.
- Changes to connection, reconnect or availability logic need a description of
  how they were tested. Say whether the test used real hardware (adapter or
  proxy model) or only mocks.

## Casambi specifics

- The library stores its cache per network under
  `.storage/casambi_bt/<address in lowercase, without colons>/`. Always derive
  this key with `cache_uuid()`, never from the raw address.
- A cached session skips the login, so the password is not verified while it
  is valid. Code that checks credentials (config flow, reauth) must do so
  against the cloud, not against the cache.
- In offline mode the integration never contacts the Casambi cloud. New code
  must keep working without the cloud and must not add cloud calls to this
  mode.

## Tests

- Every bug fix comes with a test that fails without the fix and passes with
  it. Check this before you push.
- Tests use `pytest-homeassistant-custom-component`. Never make real network
  or Bluetooth calls.
- There are two kinds of tests:
  - Most tests replace the library with the test double in
    `tests/conftest.py`.
  - Contract tests (`tests/test_library_contract.py`,
    `tests/test_password_verification.py`) run the real library against a
    fake Casambi cloud and replace only the Bluetooth connection. Add one
    whenever the behavior depends on the library, e.g. on the order of
    callbacks or on the cache format.
- Write files only to `tmp_path`, never into the shared test configuration
  directory.
- Keep tests independent of each other and of their order.

## Commits

- Write the subject in the imperative, at most about 72 characters, without
  a trailing period (e.g. `Fix cache invalidation in config flow`).
- The body explains why the change is needed and what was wrong, not only
  what changed.
- Reference issues with the full form, e.g.
  `Fixes lkempf/casambi-bt-hass#170`.
- Keep the original author when you take over someone else's commits
  (`git cherry-pick`), and don't squash them into your own.
- Each commit must pass the quality gates on its own.

## Library changes

- Changes to `casambi-bt` follow the checks of that repository (`ruff`,
  `mypy`, `pytest`). Don't add new `mypy` errors.
- Test library changes in the integration by installing the library from
  source (see [DEVELOPMENT.md](DEVELOPMENT.md)) and by running the contract
  tests.
- Releases of the library are built from version tags in its public CI.
- The pin in `manifest.json` and `requirements_test.txt` may point to a
  tagged build of the fork (`vistalba/casambi-bt`) while the changes are
  under review upstream. Pin a tagged commit, never a branch. Switch back to
  the PyPI release of `lkempf/casambi-bt` once it contains the changes.

## Reviewing pull requests

- Check the change against this document and run the quality gates on the
  merged result.
- Check that `quality_scale.yaml` still matches the code.
- For connection-related changes, check that:
  - no reconnect path can end without a retry,
  - state is updated before callbacks run,
  - every connection is closed on every error path,
  - unload cannot hang.
- Name the risks you found and describe what you tested.
